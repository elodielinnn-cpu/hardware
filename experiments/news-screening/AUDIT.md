# 新闻筛选检验方法

## 本批如何执行

本批只有 48 条，第一轮全量审阅，覆盖 6 条入选、8 条待定和 34 条排除。全量标注后才能计算本批漏收情况。审阅表已经生成在 `outputs/news-screening/audit/4c92e2cb37ce/review.csv`，冻结原文和系统结论保存在同目录的 `baseline.json`。

1. 打开 `review.csv`，先隐藏右侧以“系统”开头的列。先读“已抓取原文”和原文链接，独立做业务判断。表格按稳定编号排序，避免只审入选新闻。
2. 每行填写“人工结果”和“人工理由”。结果填写入选、待定或排除。入选需要有具体变化、具体对象和业务对应。关系无法确认或证据不足时填待定。
3. 人工判为入选的行，再填写“人工关系”（直接或明确间接）、“变化对象”“具体变化”“对应产品”“变化原句”“业务或影响原句”。两个原句可以相同，但必须足以分别支持变化与业务对应。
4. 如果网页全文有依据，而已保存内容没有，原样粘贴必要段落到“补充原文”，在“误差环节”填抓取。审阅人提供的补充内容单独标记，事实核验由审阅人负责。
5. 展开系统列对比。发生分歧时，填写“误差环节”，可填抓取、事件识别、业务范围、对象对应、因果方向、时效或其他。抓取缺失先修来源或提取，事件识别漏掉才补事件规则，业务范围缺项才补业务表。
6. 另请一位业务同事复核所有分歧和全部“明确间接”入选。分歧仍未解决的保留待定。没有第二位审阅人时记录单人审阅限制。

## 复杂关系逐项检查

| 检查项 | 可执行判断 | 常见错误 |
| --- | --- | --- |
| 变化对象 | 给对象写出产品、型号或企业名 | A 型 GPU 发生变化，却借用 B 型 GPU 的影响 |
| 业务对象 | 指出对应哪个具体产品或制造环节 | 只有公司名、AI、汽车或服务器大类 |
| 因果方向 | 用原文串出“变化对象 → 改变的要求 → 对应产品” | 把“液冷改善 GPU 散热”反推成“GPU 升级要求新液冷” |
| 事实与推测 | 区分已发生、正式计划、预测和传闻 | 把 could、可能、研究中写成实际采用或量产 |
| 时间 | 核对变化发生时间，识别旧案例和背景回顾 | 新文章引用旧产品，旧事件被当成新变化 |
| 引用范围 | 回到正文定位原句，检查前后否定和条件 | 摘了“需要”，却漏掉前面的“并不” |
| 内容归属 | 检查原句属于正文还是推荐、广告、评论 | “上一篇”里的硬件新闻使当前文章入选 |

例如，新闻说“GPU A 的功耗提高，要求冷板采用新的流道设计”，可以对应明确间接关系。新闻仅说“GPU A 性能提高，服务器里有冷板”，关系依据不足。这里的例子用于解释标注标准，未计入真实新闻的人工结论。

## 把漏抓与漏筛分开检查

在同目录的 `coverage.csv` 中，通信与数据中心、汽车各挑 4 篇近期、明确应关注的真实新闻，尽量来自不同来源，包括一手公告。填写标题、链接、业务、人工应收录（是或否）和原因。

- URL 不在冻结候选池时，先检查是否已有同一事件的其他报道，再查来源未接入、来源抓取失败、每源 20 条上限、时间范围、重复处理或业务范围过滤。
- URL 在候选池、人工认为应入选却被排除时，属于候选池内的错排除。
- 人工认为应入选但系统留待定时，单独记录为待定未放行，检查是否缺证据或规则过严。

覆盖清单的适用范围为所选定案例的采集覆盖。

## 标注后如何自动计算

在项目目录运行以下命令，或将填写好的 CSV 交回当前任务执行。

```sh
node experiments/news-screening/audit.mjs score outputs/news-screening/audit/4c92e2cb37ce
```

如果另存为其他路径，可以在命令最后加上编辑后 CSV 的路径。程序保留冻结版本的原始结果，用当前规则重算相同原文，在该批次目录生成 `score.md` 和 `score.json`。评分使用冻结的测试输入。

- 入选符合率为“人工也判入选的系统入选数 / 已标注的系统入选数”。人工判待定的自动入选，也算不符合自动入选条件。
- 人工入选召回率为“系统入选且人工入选数 / 人工入选总数”。系统排除和系统待定分别统计。
- 单独报告仅使用已抓取证据的子集，便于区分抓取缺失和规则判断问题。
- 分母为零时显示未计算。尚未标注的行不计入指标，报告同时显示标注进度。
- 这两个比例只描述本批候选。DCD 等未抓到的新闻由覆盖清单另查。

当前人工标注进度为 0/48，统计报告处于待标注状态。

## 修改规则后的回归

每个确认的错例都应保存原句、预期结果和错误环节。可复现的对象串用、因果方向、否定或推荐链接污染，补入 `test.mjs` 后再改对应规则。再次执行上面的评分命令，检查该错例是否纠正，以及其他原本正确的记录是否退化。

第一轮建议目标为入选符合率至少 90%、人工入选召回率至少 80%，并且消费电子、明显无关内容、对象串用和因果倒置的误入为零。比例同时报告分子、分母。当前批次标注完整后，再使用下一批不同日期或来源的新闻做独立验证，同事件重复报道应先合并考虑。

下一批运行抓取后，可以用 `node experiments/news-screening/audit.mjs prepare` 生成新的冻结批次。程序为每批生成独立目录，并保留已有人工填写的审阅表。

## 来源失败的复查

```sh
node experiments/news-screening/diagnose.mjs
```

输出位于 `outputs/news-screening/source-diagnostics.json`，记录请求地址、最终地址、HTTP 状态、内容类型、服务器、验证页标记和时间。诊断保留必要字段，响应 Cookie 不写入结果。

本次实际对比得到以下结果。

| 检查对象 | 结果 | 已确认原因 |
| --- | --- | --- |
| DCD 的三个 RSS 地址及主页 | 全部 HTTP 403，`cf-mitigated: challenge`，标题为 Just a moment | 返回 Cloudflare 验证页，RSS 内容尚未返回 |
| ADAS & Autonomous Vehicle International 的 RSS | HTTP 200，10 条新闻，含多段原文 | RSS 可访问 |
| 上述汽车来源抽查两篇正文 | HTTP 403，服务器为 Microsoft-Azure-Application-Gateway/v2 | 正文请求被网关拒绝，响应未透露具体规则 |

正常抓取入口也已复跑，汽车来源本批 10 个正文请求均返回 403，均通过明确标注的 RSS 节选提供证据。当前尚无法从响应确认汽车网站具体按 IP、地区、请求特征还是其他规则拒绝请求。

验证页和 403 应记录来源不可用或正文不可用。RSS 节选足够支持判断时使用节选，否则留待定。DNS、超时、429 与提取不到正文分别记录，便于下一次运行选择正确的处理方式。
